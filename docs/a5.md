# A5 运行与工程结构

## 环境与运行

A5 对应 Ascend950 系列。硬件探测会把 `Ascend950PR`、
`Ascend950PR_9579`、`Ascend950DT` 等设备名称归一化为 `Ascend950`，
供 capability 筛选与缓存使用；实际设备名称仍可通过 torch_npu 查询。

在仓库根目录创建独立环境：

```bash
conda env create -f environment-a5.yml
conda activate flashinfer-a5
source /usr/local/Ascend/cann/set_env.sh
python examples/a5_smoke.py
```

已有该环境时只需执行后三行。CANN 路径按实际安装位置调整。
环境文件选择 Python 3.11、PyTorch 2.10.0 CPU 版、
torch_npu 2.10.0.post7 和 triton-ascend 3.6.0，依据
[Triton Ascend 的 CANN 9.2 配套说明](https://triton-ascend.readthedocs.io/en/v3.6.0/quick_start.html)。
驱动、固件和 CANN 由系统提供，conda 文件只安装 Python 依赖及本工程。
`torch` 的 CPU wheel 提供框架，NPU 执行由 `torch_npu` 注册的后端完成。

样例始终用公开 API 在 NPU 上执行，再与显式选择 `backend="reference"`
的 CPU 结果比较；没有 NPU 或不属于 Ascend950 系列时会报错。
可以按算子域选择样例或指定可见设备索引：

```bash
python examples/a5_smoke.py --case gemm --device 0
python examples/a5_smoke.py --case moe
python examples/a5_smoke.py --case norm
```

`--case` 还支持 `rope`、`decode`、`cascade`；默认 `all`。
样例检查正确性，不用于比较性能。

## 当前源码的职责

| 位置 | 作用 |
| --- | --- |
| `flashinfer/norm.py`、`rope.py`、`gemm.py`、`fused_moe.py`、`cascade.py`、`decode.py` | 公开 API、输入签名、调用调度器 |
| `flashinfer/runtime/` | 硬件探测、capability、注册表、调度和决策缓存 |
| `flashinfer/cann/` | torch_npu/ACLNN 算子的参数与布局适配 |
| `flashinfer/triton/` | 延迟加载的 Triton Ascend kernel；目前包含 Gemma 融合 RMSNorm |
| `flashinfer/operators/`、`flashinfer/ascendc/` | 公共逻辑定义与原生后端的类型化声明、runner；计算本体位于 `csrc/kernels/<domain>/<op>/op_kernel/arch35/` |
| `flashinfer/reference/<domain>/<op>/` | 显式选择的 CPU 数值参考及 runner；旧 `runtime/reference_kernels.py` 为兼容入口 |
| `flashinfer/attention/` | Attention 的 metadata、plan/run、provider、量化、ABI 等框架契约 |
| `flashinfer/jit/`、`aot/`、`attention/jit/` | 通用编译/缓存/发布与 Attention 领域的计划、编译身份协议；CATLASS FA 是独立原生 eager 路线 |
| `tools/metadata/`、`build/generated/` | 前者存非派生契约，后者存生成资源；`flashinfer/data/` 仅在构建输出与安装包中存在 |
| `tests/` | 主机契约、调度、参考实现及 NPU 数值测试 |
| `examples/a5_smoke.py` | A5 公开 API 的可运行样例与 CPU 对拍 |

当前可执行算子的主链路为：

```text
公开 API → build_signature → current_hardware → dispatch
        → registry 中选定的后端 runner → CANN / Ascend C / Triton → NPU
```

Reference backend 需显式选择，不参与默认的 NPU 路由。
同一 `op` 的后端布局、A2/A3/A5 目标选择与共享 runner 规则见
[作者声明与资源交付](authoring-and-resources.md)；A2 arch22 的 GMM/SFA 不属于本页 A5 验证范围。
通用 `runtime` 注册表和 `attention` 内的 provider/capability 框架是两套
不同的接口契约；前者已有可执行 CANN runner，并不意味着后者已经接入真实 provider。

## A5 算子路径

| 公开接口 | A5 实现 |
| --- | --- |
| `rmsnorm`、`fused_add_rmsnorm`、`gemma_rmsnorm` | CANN 原生 RMSNorm 系列 |
| `layernorm` | `torch.nn.functional.layer_norm` 的 NPU ACLNN 实现 |
| `gemma_fused_add_rmsnorm` | Triton Ascend，自定义 FP32 累计 kernel |
| `apply_rope_with_cos_sin_cache_inplace` | `npu_rotary_mul`，支持 Neox/interleave 和部分旋转 |
| `cudnn_batch_decode_with_kv_cache` | `npu_fused_infer_attention_score`，分页 KV 与 GQA |
| `merge_state` | `npu_attention_update` |
| `bmm_fp8`、`gemm_fp8_nt_groupwise` | A5 FP8 `npu_grouped_matmul`，支持 E4M3/E5M2 |
| `fused_moe` | 单卡专家分组 GEMM、SwiGLU 和路由聚合 |
| `fp8_per_tensor_scale_moe`、`fp8_block_scale_moe` | FP8 专家分组 GEMM 级联，中间激活动态量化回 FP8 |

FP8 分组 GEMM 使用设备端 int64 `group_list`、堆叠权重、单位 scale
和显式 FP32 输出，再应用调用方的 scale。这样避免旧 `List[int]` 接口，
并保留外部缩放前点积的动态范围。
参见 [torch_npu 分组 GEMM 契约](https://github.com/Ascend/op-plugin/blob/master/docs/zh/custom_APIs/torch_npu/torch_npu-npu_grouped_matmul.md)。

CANN 的 Stack、RepeatInterleave 和索引路径尚未全部支持 FP8。
这些纯数据搬运使用等宽 `uint8` 视图，随后恢复原 FP8 dtype；
不经过 BF16 或 CPU 反量化，FP8 位模式保持不变。
MoE 的中间 FP8 量化会引入额外误差，因此对照保留 FP32 中间激活的
CPU 参考时，还需检查整体相对范数误差。
现有 MoE 编排包含计数的设备到主机同步和 Python 分块循环，
这里只提供正确性路径，尚未完成融合与性能优化。

## 验证与范围

```bash
python -m pytest -q tests/test_hardware.py tests/test_a5_npu.py \
  tests/test_norm.py tests/test_rope.py tests/test_cudnn_decode.py \
  tests/test_cascade.py tests/test_gemm_fp8.py tests/test_fused_moe.py
```

`test_a5_npu.py` 只在真实 Ascend950 设备上运行，覆盖 FP8 输入类型组合、
输出复用、外部缩放前溢出、groupwise scale 布局、空专家组及逐字节搬运。
非 A5 环境会跳过这些测试，不能把跳过视为 NPU 正确性证据。

此处的分页 Decode 是上述独立 CANN runner。完整 `BatchAttention`、
prefill、量化 KV provider、自研 Attention JIT 和多卡 EP 不属于这个单卡样例的支持声明。
当前 Attention 框架还引用了通用 runtime 中缺失的 `SchemaError`、
`QuantSpec`、artifact/ABI 等类型，因此相关历史测试可能在收集阶段失败；
该问题与 A5 算子 runner 的运行是独立的。

CANN `set_env.sh` 会把系统 Python 包加入 `PYTHONPATH`。
若系统 CANN 的 TE/GE wheel 只提供其他 Python ABI，需要匹配的 CANN
组件才能使用这些编译工具。检查 conda 自身依赖可执行
`PYTHONPATH= python -m pip check`；该命令不检查外部 CANN wheel 的 ABI。
