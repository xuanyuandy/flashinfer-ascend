## 2:30–5:30 这段怎么讲（最有说服力的三件）

1. **契约 v2 + 纵向闭环**：此前 recipe 护栏直接拒绝 AIC+AIV、非零 workspace、
   动态 tiling、变参 ABI，所以复杂算子根本接不进来。现在扩到 v2 并写了独立校验，
   **登记表从空到 2 条生产算子**，「登记 → 自动 AOT 消费 → 受控 JIT 回落」在真机走通，
   **corrupt 产物即使 JIT 开着也拒绝**。
2. **ABI 门禁从红转绿，且不是靠改 golden 糊弄**：定位到单一根因、验证无人依赖旧值、
   并且明确没有声称新旧语义等价。（会被追问，细节见 B3）
3. **图模式机制跑通**：1 次捕获 8 次重放、**误差 0**、四类负例全拒——
   但**覆盖面只有 1/81**，这个数我主动说。

## 9:30 收尾 + 要资源（照这个意思念）

> 「全量对标两个月做不到，这个我写在文档第一句。能承诺的是 P0 七项，每项都有验收标准。
> 我特意**没有写人力数字和精确工期**——那取决于目标 workload 和设备矩阵定在哪里。
> **这部分想请各位帮我们收敛，收敛完我才能给出可信的排期。**」

最后一句是把球递回去，同时也是在要资源。比「我们会努力」有用得多，
而且顺带解释了为什么路线图里没有工期——不是没想清楚，是前提没定。

# 第一部分：讲什么（建议 35 分钟）

## 0. 开场定调（2 分钟）—— 先把结论和边界给出去

> 「这个项目是对标 FlashInfer Python 接口与语义的昇腾推理算子库。
> 我先把结论放前面：**单点能力已被真机验证、工程契约相当完整，但生产交付尚未闭环。**
> 它既不是一个只有骨架的 PPT 项目，也还不能说已经对齐上游或可以生产部署。
> 今天想请各位重点看三件事：分层是否合理、关键取舍站不站得住、下一步该投哪里。」

**为什么这样开场**：专家最反感的是"汇报时全是绿灯，问两句全是坑"。
先自己把定性说死，后面所有数字都变成佐证而不是辩护。

## 1. 定位与边界（4 分钟）

讲清楚**我们负责什么、不负责什么**（文档 §1）：

```
上层：vLLM-Ascend / SGLang / 自研 serving        ← 不在本仓
         ↓ 调用算子 API（对标 FlashInfer 的名字与语义）
本仓：算子 API 语义对标 · 后端选择 dispatch
      构建/缓存/加载（JIT · AOT）· 入图资源契约
         ↓
底座：torch_npu / CANN·ACL / Ascend C / bisheng / triton-ascend / catlass
```

**明确不做**：CUDA 二进制兼容、逐行翻译 CUDA kernel、训练与 autograd、
图的切分与生命周期（FULL/PIECEWISE、分桶由调用方负责）。

一句必须说的话：
> 「API 名字和上游一样，**不代表所有参数组合等价**。这是读这个仓库最容易踩的误解，
> 我们在文档里用 `[V]/[P]/[G]` 三档标记就是为了防止这个误读。」

## 2. 架构主干（8 分钟）—— 一次调用怎么走

```
调用方 Tensor / out / backend 请求
  → API 校验与输出准备
  → InputSignature + HardwareSignature
  → dispatch：capability / target / policy 过滤 → tuning 记录或默认排序
  → descriptor.kernel_id → 已绑定 runner
  → CANN 算子 / Ascend C 产物 → NPU → 写回
```

**要讲的三个设计取舍**（这是专家真正想听的）：

1. **构建身份用内容寻址**：真实 cache key 是 `JitSpec.fingerprint` ——
   `JitSpec.to_dict()` 的 canonical JSON SHA-256，绑定源码摘要、编译选项、依赖、ABI。
   **代价**：身份闭包必须准确，改源码就得重算摘要、重新冻结 spec。
   **收益**：可审计、可复现，能区分"同输入但不同源码/编译选项"。
   对比上游用 URI + Ninja 新鲜度检查——两种都成立，不是谁更完整的问题。

2. **登记表声明在前、执行在后**：descriptor 声明能力（dtype/SoC/shape 范围/入图性质），
   dispatch 按声明过滤，**不匹配就在选型阶段拒绝，而不是算错**。

3. **契约分版本而不是放开**：v1 的护栏（定形 tiling / AIC-only / 零 workspace / 三参数）
   原条件一字未改，v2 另立一套并有自己的校验。老路径行为不变。

## 3. 四条轴线（12 分钟，每条 3 分钟）

每条都用同一个句式：**能力边界是什么 → 最近做了什么 → 还差什么**。

### JIT
- **边界**：显式构建、内容缓存、原子发布与加载已可运行且有真机验证；
  生产 dispatch 自动编译与全库缓存治理尚未接通。
- 冷热路径分离：hit 走校验后的 loader；miss 要过 policy → per-spec flock → 锁内复查
  → staging 编译 → 校验 → 不可变 generation → 原子替换 symlink。
- 失败保留诊断，已发布 generation 不被原地覆盖；并发首用由锁内复查去重。
- **一处 API 债务要主动交代**：顶层导出的 `build_cache_key` 是 legacy 死代码，
  非测试调用为零，还有测试专门 monkeypatch 成 `forbidden` 断言真实路径不调它。应弃用。

### AOT
- **边界**：产出可以、显式加载可以、**运行期自动发现→命中→绑定 runner→受控 JIT 回落已接通**；
  安装矩阵、provider 分包、多 package identity 仍缺。
- **四类错误分流**（这条专家会认可）：
  missing 按 JIT policy 决定是否回落；**corrupt / incompatible / load error 一律拒绝且不回落**。
  特别是 corrupt——**JIT 开着也拒绝**，不能让损坏产物被当成"没有产物"而静默重编译掩盖掉。
- 真机证据：`source=aot, compiler_calls=0`，以及 corrupt 场景 `policy=enabled` 仍 `fallback=false`。

### 图模式
- **边界**：torch.library 有真实窄入口；aclgraph **仅 1 条**受限 single-decode descriptor；
  batch 的固定资源与 plan 冻结**尚未接成通用 replay**。
- 三段机制：捕获外 plan/预热并冻结身份 → 捕获内 run 只消费已持有资源 → 重放前 `before_replay` 更新参数。
- 真机：1 次捕获 8 次重放（KV 长度 63/1/17/128/513/1024/3/63），
  **输出与 LSE 误差均为 0**（与 eager 逐位一致）；四类负例全部明确拒绝。
- **主动说**：`1/81` 是 descriptor 口径的**能力声明**，不是"算子实测通过率"。
  类名带 `CUDAGraph`、参数带 `use_cuda_graph` 都不构成入图证据。

### 自定义算子接入
- **边界**：recipe/CMake/显式加载/torch.library 已串通；
  v2 放开了 AIC+AIV、动态 workspace、动态 tiling、变参 ABI；两条生产算子已接公共入口。
- native 与 catlass **共用**编译器、store、loader，不是两套 runtime；
  catlass 只是多一条固定 revision 的依赖声明，且 **wheel 不自带 catlass 头树**。
- 接入交付件已成清单（33 项，native/catlass 双列）+ 操作指南。

## 4. 诚实的缺口（5 分钟）—— 自己讲，不要等专家挖

> 「下面这些是我们自己列的缺口，不是今天被问出来的。」

| 缺口 | 现状 |
|---|---|
| **性能** | **全程没有做过同口径性能测量**。文档里没有任何性能声称 |
| 入图覆盖面 | 1/81，`CAPTURE_SAFE` 为 0；两条生产自研算子都不可入图 |
| 生产自研算子数量 | 只有 2 条（一条 native、一条 catlass FA） |
| 能力域覆盖 | 9 个域有 op，**8 个域为空或仅有壳**（MLA、稀疏、通信、量化算子、GDN/Mamba、训练辅助、trace、autotuner） |
| 数据内容驱动 tiling | 契约表达不了（依赖张量内容而非 shape 符号），未验证 |
| 多 package identity | 单进程只能激活一个 |
| CANN 运行时版本兼容 | 只校验 target/spec，不比较当前 CANN 版本 |
| 下游集成 | **没有 vLLM-Ascend / SGLang 实际接入证据** |

## 5. 路线图（8 分钟）—— 先说不可能，再说能做什么

> 「两个月内完成与上游的**全量**对标是不可能的。上游 42 个直接子包、2656 个 .py 文件；
> 我们 9 个能力域有 op、8 个域为空。这个差距不是靠加人能在两个月内填平的。」

然后给**可操作的「对标」定义**（文档附录 B.1），重点讲那张"不算达成"表：

| 对标层 | 什么才算达成 | 不算达成 |
|---|---|---|
| 接口 | 参数/dtype/layout/alias/异常边界有矩阵 | 仅 import 成功或函数同名 |
| 执行语义 | 承诺输入有数值证据，不支持的明确拒绝 | 静默丢 mask / 量化选项 / 广播差异 |
| 生命周期 | plan/run、预热、workspace、capture/replay 可复现 | 仅提供 plan 或 `use_cuda_graph` 开关 |
| 交付 | 安装后公共入口可运行，AOT/JIT/禁编译行为清楚 | 开发机显式加载一个目录成功 |
| 性能 | 同数学/shape/误差/测量政策下可复验 | 未测先承诺追平或加速比 |

P0 七项各有「缺口→依赖→验收→风险」+ 相对规模，**不编人力和工期**。
要强调：**P0-E（生产算子最小图闭环）自评为"大"**，且未过门禁就记作 P0 未达。

# 第二部分：Q&A 预案

> 每条给：**专家为什么问 → 怎么答 → 证据 → 不要说什么**

## A 类：定位与价值（最可能开场就问）

### A1「这一层的价值是什么？直接调 CANN aclnn 不行吗？」

- **为什么问**：43 个 op 里 40 个 descriptor 是 CANN backend，看起来像个转发层。
- **怎么答**：
  > 「价值不在于替换 CANN，而在于三件 CANN 不提供的事：
  > 第一，**接口语义对标 FlashInfer**，让 CUDA serving 栈迁移成本可控；
  > 第二，**确定性、可解释的后端选择**——给定输入签名和硬件快照，选哪个 kernel 唯一且可复现，
  > 且不支持的组合在选型阶段就被拒绝，不会算错；
  > 第三，**自研算子的交付体系**——CANN 覆盖不到的地方（比如 Add+Gemma 融合），
  > 我们能自己编、自己缓存、自己分发，而且是可审计的。」
- **证据**：`gemma_fused_add_rmsnorm` 是全仓唯一走 Triton 的算子，正因为 CANN 侧缺这个融合。
- **不要说**：「我们比 CANN 快」——没有任何性能数据。

### A2「为什么不直接 fork 上游改？」

- **怎么答**：
  > 「上游的实现底座是 CUDA/NVCC/cubin/CUTLASS，设备代码和装载格式都不同，
  > 能复用的只有**接口语义和生命周期设计**，而这部分我们确实是照着对标的。
  > fork 会把大量 NVIDIA 专有路径（MNNVL、NVSHMEM、CUDA IPC、PDL）一起背上，
  > 这些在昇腾上没有对应物。」
- **补一句分寸**：「但也要承认，不 fork 的代价是我们得自己维护一套 adapter 和交付体系。」

### A3「和 vLLM-Ascend / SGLang 怎么配合？谁在用？」

- **这是我们的弱点，要如实答**：
  > 「目前**没有下游实际接入的证据**。我们做的是算子库这一层，
  > 图的切分、FULL/PIECEWISE、分桶都留给调用方——这个职责边界我们认为是对的，
  > 但'边界对'不等于'已经接上了'。下游集成不在当前已验证范围内。」
- **不要说**：「vLLM 可以直接用」。

## B 类：质量与证据（专家最爱挖的地方）

### B1「1975 个测试通过说明什么？」

- **为什么问**：测试数是最容易注水的指标。
- **怎么答**：
  > 「说明的是**回归没破**，不说明覆盖面。我更愿意提的是另外两个数：
  > 一是 `-m real_compile` 的 **80 个用例 0 skipped**——这些是真机、真编译器、真 kernel，
  > 在没有 NPU 的环境里它们会静默跳过，所以 '0 skipped' 比 '80 passed' 更重要；
  > 二是这些测试里有**大量负例**，比如损坏产物必须被拒绝、超范围 shape 必须在选型阶段拒绝。
  > 测试数本身我不会拿来证明能力覆盖。」
- **证据**：之前基线是 1777 passed / 3 failed，现在 1975 / 0。

### B2「`[V]` 这个标记到底是什么意思？」

- **怎么答**：
  > 「`[V]` 是'有**限定范围**的运行证据'，不是'做完了'。文档图例里专门写了一句：
  > `[V]` 也不等于生产成熟、性能领先或与上游完全等价。
  > 每个 `[V]` 后面我们都带了限定词，比如 dispatcher 是'`[V]` 限选择契约'、
  > ABI 是'`[V]` 限当前冻结'。」

### B3「ABI 冻结指纹你们改了 golden，这不是把门禁拆了吗？」

- **为什么问**：这是最像"为了绿灯改测试"的动作，必问。
- **怎么答**（完整讲清因果链）：
  > 「这个质疑是对的，所以我说一下为什么它不是拆门禁。
  > 第一，**根因不是回归**：冻结值写在初始提交，当时 runtime 侧这些 ABI 类根本不存在；
  > 后来 T1 重建了它们但复现不出原序列化。T1 的报告里早就写明了这是遗留，
  > 而且明确说'未通过硬编码映射或放宽测试掩盖'。
  > 第二，**是单一根因**：`ATTENTION_KERNEL_ERROR_ABI` 以完整 dict 嵌入两个 binary 的哈希，
  > 再经 wire header 传播，一处漂移导致 4 个冻结值失配。
  > 指纹算法本身没问题——同文件 5 个 POD struct 的指纹至今仍与初始值一致。
  > 第三，**改之前验证了无人依赖旧值**：检索了仓库代码、manifest、缓存、
  > 以及已构建出的 op-package，旧值只出现在测试 golden、pytest 日志和历史文档里。
  > 第四，**我们没有声称新旧等价**——原定义没能恢复，这一条写在决策记录和附录 A 里。」
- **证据**：`docs/reports/abi-refreeze-2026-10-25.md`。

### B4「数值精度怎么保证？」

- **怎么答**：
  > 「每个生产算子都有对参考实现的数值用例并给出容差：
  > FA 对 catlass 自带 golden，最大绝对误差 `1.22e-4`，容差 `1e-3`；
  > matmul_bias_silu 对 fp64 参考，最大 `0.0078`，容差 `0.008`；
  > 图模式重放与 eager 的误差是 **0**（逐位一致）。
  > 但要说清楚：这些是**声明 envelope 内**的若干组 shape，不是穷举。」

## C 类：架构取舍（专家会挑设计）

### C1「入图只有 1/81，这个功能有意义吗？」

- **怎么答**：
  > 「现在的意义是**机制打通和口径诚实**，不是覆盖面。
  > 这一条路线我们做到了：捕获外 plan 并冻结身份、捕获内只消费已持有资源、
  > 重放前显式更新参数，四类负例都拒绝——包括漏调参数更新就重放，
  > 那个如果静默沿用旧参数就是正确性地雷。
  > 但我必须说清楚两件事：第一，这个公共接口**写死在单一配置**
  > （head_dim=64、8/2 头、KV 容量 1024），不是通用 single-decode 图接口；
  > 第二，**两条生产自研算子都不可入图**，这是附录 B 里 P0-E 那一项，我们自评为'大'。」
- **不要说**：「图模式已支持」。

### C2「为什么公共接口要写死在一个配置上？」

- **怎么答**：
  > 「因为 descriptor 的能力声明只覆盖这一条已验证路线。我们宁可接口窄但声明诚实，
  > 也不愿意放开参数然后在未验证的组合上出问题。
  > 扩大 envelope 要同步改四个地方——recipe 的 shape_constraints、descriptor 的 capability、
  > host 侧实际支持、dispatch 门禁和拒绝测试。漏一处就是'声明支持但算错'。」

### C3「catlass FA 迁过来了，但 envelope 这么窄（batch=1、定长、FP16、D=128），有什么用？」

- **这题要答得细，否则会被认为是演示品**：
  > 「它的价值不在于这个 envelope 本身能跑多少业务，而在于**证明了一条复杂算子的接入路径**。
  > FA 需要 AIC+AIV 跨核同步、非零动态 workspace、host 动态 tiling、四个以上张量——
  > 这四条在此之前是被 recipe 的护栏**直接拒绝**的。
  > 为了接它，我们把契约扩到 v2 并写了独立校验，而且是先用一个中等算子
  > （matmul_bias_silu）打通闭环，再上 FA。
  > 另外有一点必须讲清：**定长限制来自 catlass 那个例子本身**——
  > 它的 host 代码里就写着拒绝 `isVariedLen > 0`。
  > 但也正因为如此，**这次迁移并没有证明 v2 能表达数据内容驱动的 tiling**，
  > 那项能力仍然是未验证的缺口。」
- **这段的分寸**：既说清价值，又不让"迁了 FA"被外推成"支持 FlashAttention"。

### C4「两条生产算子，却做了这么多契约和基础设施，是不是过度设计？」

- **这是个尖锐但公平的问题**：
  > 「这个质疑我接受一半。基础设施确实超前于算子数量。
  > 但反过来说，前面的顺序如果反过来——先堆算子再补交付体系——
  > 会出现大量没法审计、没法在无编译器环境部署的产物。
  > 我们现在的状态是**路修好了、车还少**，下一步的重点就是上量，
  > 这也是附录 B 里 P0 的主线。
  > 判断标准我写在路线图里了：下一个算子接入需要多少交付件，已经列成 33 项清单，
  > 如果接入成本降不下来，说明基础设施的设计有问题。」

## D 类：路线图与资源（领导层最关心）

### D1「两个月到底能做到什么？」

- **怎么答**：
  > 「全量对标不可能，这个我写在附录 B 第一句。
  > 能承诺的是：**选定的推理关键路径，在明确的支持矩阵内，
  > 具备可对照验收的接口、语义、生命周期和部署行为。**
  > 具体是 P0 七项，每项都有验收标准。P1 争取补 1~2 个空域的受限子集。
  > P2 明确不在两个月内，并说明原因。」
- **关键补充**：「我特意没有写人力数字和精确工期，因为那需要先确定目标 workload 和设备矩阵。
  这部分想请各位帮我们收敛。」

### D2「那 8 个空的能力域怎么办？」

- **怎么答**（这里的区分很重要）：
  > 「要分成两类。
  > **有意不对标的**：MNNVL、NVSHMEM、CUDA IPC 这些 NVIDIA 专有通信实现，
  > 昇腾上没有对应物，不做是合理取舍。
  > **尚未补齐的**：HCCL 路径的通信、MLA、稀疏 attention——
  > 这些是实打实的缺口，不能跟上面那类混在一起算作'有意不做'。
  > 文档里这两类是分开列的。」

### D3「优先级怎么排？」

- **怎么答**：
  > 「按交付影响面。最高优先是**打通生产交付闭环**而不是扩大算子清单——
  > 因为有产物却不能被公共 API 自动消费，会破坏'装上就能用'的部署预期。
  > 其次是生产算子上量和图能力。
  > 扩大算子清单应该以闭环为前提，否则只是增加更多未连接的接口。」

## E 类：工程与维护

### E1「跟 CANN / catlass 的版本绑定怎么管？」

- **怎么答**：
  > 「catlass 是在 recipe 里**固定 Git revision 加头文件摘要**，
  > 而且 wheel 不自带 catlass 头树，接入方要自己准备 checkout，缺失时构建阶段明确报错。
  > CANN 这边要如实说：**我们目前只校验 target/spec，不比较当前运行时 CANN 版本**，
  > 构建时记录的版本不等于部署时 ABI 兼容。这是已知缺口，在附录 B 的 P0-C。」

### E2「新增一个算子要多久/要做什么？」

- **怎么答**：
  > 「交付件已经列成清单：33 项，native 和 catlass 分两列。
  > 还有一份操作指南，写了决策树（什么时候必须用 v2）、按序工作流，
  > 以及我们实际踩过的 10 个坑——比如改源码忘了重算摘要、解释器用错导致真机用例静默跳过。
  > 时间我不敢给数字，因为取决于 kernel 本身的复杂度；
  > 但**接入流程本身已经不是未知数了**。」

### E3「这套东西怎么防止退化？」

- **怎么答**：
  > 「几道门禁：登记表的计数和集合断言是**钉死精确集合**的，
  > 新增生产 kernel 必须被显式确认，混不进去；
  > ABI 有冻结指纹；入图能力声明有测试断言守着
  > （比如断言某条 descriptor 必须是 `NOT_CAPTURABLE`），防止为了好看提升等级；
  > corrupt 产物必须拒绝也有负例守着。」
